# Development data location

`TimeTracker.md` is the single source of truth for the app during development.

It is intentionally readable and editable with Notepad, Notepad++, or Obsidian. The app will eventually allow the user to select another folder; no feature should hard-code this location outside the storage-location service.

The file is ignored by Git because it may contain personal activity history.

## Format 2 contract

- The first line is `# Time Tracker`.
- `## Metadata` stores the next app-generated numeric activity ID.
- `## Activities` stores the visible name, optional daily/weekly/monthly quotas, and status for each activity.
- IDs are generated by the app, never reused, and must not be edited manually.
- Future entries are appended beneath the horizontal rule, under a `## YYYY-MM-DD` date heading.
- The app will never create a database, cache, or hidden session file.

## Tracking events

The timer writes one human-readable line per state change:

```md
- 09:00:00 | START | 1 | xAI
- 10:15:18 | PAUSE | 1 | xAI
- 10:30:04 | RESUME | 1 | xAI
- 12:00:31 | STOP | 1 | xAI
```

The current timer state is restored from the latest valid event sequence when the app launches.

New events always use `HH:mm:ss` and the V2 numeric activity ID. Older V1 event lines are intentionally treated as faulty data at launch; choosing repair backs up the original and migrates every recoverable entry to V2.

## Repair policy

Repair is always explicit. It first copies the untouched active log to `backups/`, then rebuilds the active log from valid and recoverable data.

- V1 name-only events are mapped to an existing matching activity ID, or assigned a newly generated non-competing ID.
- Duplicate activity names are merged under the lowest numeric ID.
- An event whose ID conflicts with its visible name is treated as the visible name's activity; a new ID is generated if needed.
- Event sequences that remain invalid after migration are excluded and counted in the recovery note.
